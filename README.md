### 4.1 커피 메뉴 목록 조회 API
- **문제 인식**:
    - 메뉴 목록은 조회 요청이 매우 잦아 매번 데이터베이스(DB)를 조회하면 불필요한 부하가 발생할 수 있음
    - 서버를 여러 대 띄웠을 때 각 서버의 로컬 메모리에 캐시를 저장하면, 메뉴가 품절되거나 가격이 바뀌었을 때 서버마다 데이터가 달라지는 정합성 문제 발생
- **해결 전략**:
    - **Redis 분산 캐시 적용 및 운영 전략**:
        - **언제 읽는가? (Read - Cache-Aside)**:
            - 메뉴 목록(`GET /api/menus`) 조회 시 Redis(`menus:all` 키)를 먼저 확인
            - **캐시 존재 시**: DB를 거치지 않고 메모리에서 즉시 응답 반환
            - **캐시 미존재 시 (첫 요청 또는 삭제 직후)**: DB에서 전체 목록을 읽어와 반환하고, Redis에 다시 저장(TTL 설정)
        - **언제 삭제하는가? (Evict - 다중 서버 일치 보장)**:
            - **일반 주문 시**: 캐시를 삭제하지 않고 유지하여 캐시 히트율 보존
            - **메뉴 정보 변경 시**: 신규 메뉴 등록, 가격 수정, 품절 처리(`SOLD_OUT`), 삭제 시 Redis의 `menus:all` 키를 즉시 삭제하여 모든 서버가 동일하게 최신 데이터를 서빙하도록 처리
        - **전체 캐시 키를 삭제하고 다시 읽는 이유**:
            - 메뉴 데이터는 수십~수백 건 수준으로 용량이 작아 전체 갱신 비용이 매우 저렴함
            - 캐시 내부 특정 데이터만 부분 수정하는 복잡한 로직보다, 키 하나를 삭제하고 다음 조회 시 DB에서 새로 채우는 방식이 코드 복잡도를 낮추고 데이터 일관성을 지키는 데 가장 안전함
    - **DB 조회 최적화**:
        - 캐시가 없어 DB를 직접 조회할 때는 `@Transactional(readOnly = true)`를 적용해 불필요한 영속성 컨텍스트 수정 감지(Dirty Checking) 작업을 생략하고 메모리 절약
- **기술적 선택 이유 및 대안 비교**:
    - **로컬 캐시(Caffeine/Ehcache) 대신 Redis 분산 캐시를 선택한 이유**:
        - 로컬 캐시는 네트워크 I/O가 없어 가장 빠르지만, 다중 서버 환경에서 특정 인스턴스만 메뉴를 수정했을 때 다른 인스턴스들의 캐시를 무효화(Cluster Invalidation)하기 위한 메시징 구조가 추가로 필요하여 복잡도가 급증함. 중앙화된 Redis 분산 캐시를 통해 단일 무효화 명령으로 모든 서버의 데이터 일관성을 즉시 보장함.
    - **Write-Through 대신 Cache-Aside(Lazy Loading) 패턴을 선택한 이유**:
        - 메뉴 갱신 시점에 매번 캐시를 직접 계산해 밀어 넣는 방식(Write-Through)은 쓰기 부담이 커지고 미조회 데이터까지 메모리를 점유함. 캐시 미스 시점에만 적재하는 Cache-Aside가 구현이 단순하며, TTL 만료 정책과 결합 시 메모리 효율이 가장 우수함.

### 4.2 포인트 충전 API
- **문제 인식**:
    - 사용자의 연속 더블 클릭이나 네트워크 재전송으로 인해 동일 유저의 충전 요청이 동시에 들어올 경우 갱신 손실(Lost Update) 발생 위험
    - 잔액 수정과 충전 로그(이력) 적재 간의 데이터 불일치 방지 필요
- **해결 전략**:
    - **Redis 분산 락(Redisson) 기반 요청 직렬화**:
        - 유저 고유 키(`lock:user:{id}`)로 분산 락을 획득한 후 잔액 변경 로직을 수행하여 다중 인스턴스 환경에서도 동일 유저 요청을 순차 처리
        - DB에 직접 Lock을 거는 비관적 락 대비 DB 커넥션 점유 시간을 최소화
    - **원장 데이터의 원자성 보장**:
        - `points` 잔액 수정과 `point_histories` 변동 내역 적재를 하나의 트랜잭션으로 묶어 데이터 무결성 보장
    - **입력값 방어 검증**:
        - 0원 이하의 비정상 충전 요청을 `@Positive` 을 통해 컨트롤러 진입 시점에서 원천 차단
- **기술적 선택 이유 및 대안 비교**:
    - **DB 비관적 락(`SELECT FOR UPDATE`) 대신 Redis 분산 락(Redisson)을 선택한 이유**:
        - 비관적 락은 트랜잭션이 시작되는 순간부터 DB 커넥션을 점유한 채 대기하므로, 동시 요청 급증 시 커넥션 풀(HikariCP) 고갈로 전체 시스템 장애가 전파될 위험이 있음. 대기 스레드가 DB 커넥션을 점유하지 않도록 Redis 레벨에서 먼저 동시 요청 순서를 제어하고, 락을 획득한 스레드만 실제 쿼리 수행 시점에 커넥션을 쓰도록 분리해 HikariCP 고갈을 방지.
    - **기본 클라이언트(Lettuce) 대신 Redisson을 분산 락 구현체로 선택한 이유**:
      - Lettuce의 SETNX 방식은 락 획득 시까지 지속적으로 요청을 찌르는 스핀 락(Spin Lock) 구조로 동작하여, 트래픽 급증 시 Redis CPU 및 네트워크에 과도한 부하를 유발함. Redisson은 Pub/Sub 기반 알림 방식을 사용하여 락 해제 신호가 올 때만 재획득을 시도하므로 불필요한 재시도 트래픽 없이 안정적으로 락 대기 처리가 가능함.
    - **낙관적 락(`@Version`)을 배제한 이유**:
        - 낙관적 락은 충돌 시 롤백 후 재시도(Retry) 로직을 애플리케이션에서 직접 처리해야 하며, 동시 다발적인 연타 요청 시 DB 롤백 비용과 실패율이 급증하므로 금융/포인트 성격의 직렬화 처리에 부적합함.

### 4.3 커피 주문 및 결제 API
- **문제 인식**:
    - 한 유저가 주문 버튼을 연속 클릭하거나 충전과 결제를 동시에 시도할 때 포인트 갱신 손실(Lost Update) 및 잔액 음수화 위험
    - 다수의 유저가 남은 재고가 1개인 동일 메뉴를 동시에 주문할 경우, 유저 락만으로는 방어가 불가능하여 초과 판매(Overselling) 발생 위험
    - 주문 트랜잭션 내부에서 Kafka 발행을 동기로 묶을 경우, 브로커 지연이나 일시 장애가 정상 결제된 주문까지 롤백시키는 문제
    - 메뉴 가격이 사후 변경될 때 과거 주문 내역의 결제 금액이 함께 바뀌는 정합성 문제
- **해결 전략**:
    - **유저 단위 분산 락 (동일 사용자 보호)**:
        - 포인트 충전과 동일한 Redis 분산 락 키(`lock:user:{id}`)를 사용하여 동일 유저의 요청을 순차적으로 직렬화 처리
        - DB 테이블 수준의 `CHECK (balance >= 0)` 제약조건으로 2차 방어선 확보
    - **DB 조건부 원자적 쿼리를 통한 재고 제어 (서로 다른 사용자 보호)**:
        - 단순 조회 후 자바 코드 계산(`setStock`) 대신, DB 엔진의 행(Row) 배타 락을 활용하는 원자적 쿼리(`UPDATE menus SET stock = stock - quantity WHERE id = :id AND stock >= quantity`) 적용
        - 나노초 단위로 동시에 진입하더라도 DB 레벨에서 순차 검증되어, 잔여 수량이 부족한 요청은 반영 결과(`updatedRows == 0`)를 통해 즉시 품절 예외로 안전하게 차단
    - **Kafka 이벤트 기반 트랜잭션 격리**:
        - DB 커밋 완료 시점(`@TransactionalEventListener(phase = AFTER_COMMIT)`)에 비동기로 Kafka 토픽(`order-events`)에 메시지를 발행
        - 브로커 일시 장애나 네트워크 지연이 발생해도 이미 완료된 고객의 주문/결제는 절대 롤백되지 않도록 격리
    - **주문 시점 단가 스냅샷 저장**:
        - `order_items` 테이블에 주문 시점의 메뉴 가격(`order_price`)을 기록하여 향후 메뉴 단가 변동과 무관하게 과거 거래 영수증의 정합성 유지
- **기술적 선택 이유 및 대안 비교**:
    - **메뉴별 분산 락 대신 DB 원자적 쿼리를 선택한 이유**:
        - 주문 시 유저 락(`lock:user:{id}`)과 메뉴 락(`lock:menu:{id}`)을 동시에 잡는 구조(다중 락)는 여러 유저가 여러 메뉴를 교차 주문할 때 분산 데드락(Deadlock)을 유발할 위험이 매우 높음. 단일 업데이트 쿼리의 `WHERE stock >= :qty` 조건으로 DB 엔진 자체의 행 락을 극히 짧은 순간만 활용함으로써 데드락 위험을 원천 차단하고 처리 성능을 극대화함.
    - **동기 호출 대신 비동기 Kafka 발행을 선택한 이유**:
        - 주문/결제 핵심 비즈니스 로직과 사후 분석용 데이터 수집 파이프라인의 결합도를 완전히 분리. 브로커 전송 지연이나 장애가 발생하더라도 이미 결제가 완료된 고객의 정상 주문 트랜잭션을 보호하기 위함.

### 4.4 인기 커피 메뉴 목록 조회 API (최근 7일 기준 상위 3개)
- **문제 인식**:
    - 최근 7일간의 최다 주문 메뉴를 조회할 때, 수십~수백만 건에 달하는 대용량 주문(`order_items`)을 매번 직접 `GROUP BY` 및 `SUM`으로 집계하면 심각한 DB I/O 병목 및 지연 발생
    - 대량의 통계 데이터를 Redis 메모리에만 전적으로 의존할 경우 서버 재부팅 시 데이터 유실 위험이 있으며, 히스토리성 시계열 데이터 분석이 불가능함
- **해결 전략**:
    - **일별 집계 테이블(`menu_daily_stats`)을 통한 집계 부하 경감**:
        - 주문 원장을 직접 뒤지지 않고, 일자별·메뉴별 판매량을 사전 요약한 `menu_daily_stats` 테이블 구축
        - 7일간의 데이터를 조회하더라도 탐색 범위가 "메뉴 개수 × 7일(수백 건)"로 제한되어 DB 쿼리 비용을 수천 배 이상 절감
    - **Redis 캐싱을 통한 서브 밀리초 응답 서빙**:
        - 매일 자정 스케줄러가 전날 원장을 일별 테이블에 `INSERT`한 직후, 최근 7일치 데이터를 합산하여 Top 3 랭킹을 Redis 키(`popular:menus:top3`)에 선제 적재(Cache Warming)
        - 사용자 요청 시 RDB 접근을 완전히 차단하고 인메모리에서 초고속으로 결과 반환
    - **안정적인 장애 격리 (Fallback 구조)**:
        - Redis 장애 발생 시, 가벼운 `menu_daily_stats` 집계 쿼리로 즉시 우회(Fallback)하도록 설계하여 서비스 중단 방지
- **기술적 선택 이유 및 대안 비교**:
    - **주문 시점 실시간 Redis 카운팅(`ZINCRBY`) 대신 일별 집계 테이블 + 배치 캐싱을 선택한 이유**:
        - 실시간 Sorted Set을 쓰면 "오늘 주문"은 쉽게 카운팅되지만, "정확히 7일 전 데이터만 골라서 차감(슬라이딩 윈도우)"하는 로직이 매우 복잡해지고 데이터 오차가 누적될 수 있음. 반면 일별 통계 테이블을 기반으로 매일 자정에 최근 7일치를 새로 계산해 캐싱하는 방식은 데이터 정합성이 100% 보장되며 구현 안정성이 훨씬 뛰어남.
    - **실시간 API 호출 집계 대신 스케줄러 Cache Warming을 선택한 이유**:
        - 조회 빈도가 높은 랭킹 데이터를 실시간 집계하면 특정 사용자 요청에 집계 지연 시간이 전가됨. 스케줄러를 통해 트래픽이 적은 새벽 시간대에 미리 결과를 계산해 캐시에 넣어둠으로써 모든 사용자가 균일하게 서브 밀리초(sub-millisecond) 응답을 받도록 보장함.
